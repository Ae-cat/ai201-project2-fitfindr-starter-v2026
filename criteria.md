# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
I chose 4 of 5 instead of 5 of 5 because my search is a plain keyword match.
User queries may not always contain clear keywords, so the search may only
capture some of the intended details, and spelling errors can cause it to miss
a listing entirely. Because of this, an occasional miss is expected.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
I chose 5 of 5 even though criterion 1 is 4 of 5, because this path is
different: when the search matches no listings, there is no item for the other
tools to work with, so the agent must stop every time. The stop is a simple
check for an empty list in the loop, with no model involved, so there is no
randomness that could excuse a miss.

---

## 3. Something about state

<!-- YOU WRITE THIS ONE.

     How would you know that the item your search found is the same item the
     next tool received? Name something countable or observable.

     This is the criterion people find hardest, because state failure doesn't
     look like state failure — it looks like a tool problem. Something that
     compares session["selected_item"] against what actually reached
     suggest_outfit is the shape you're after. -->

Given a query that returns at least one listing, the item stored in
`session["selected_item"]` is the same item (same `id`) that is passed into
`suggest_outfit` — 5 of 5 tries. Checked by printing the `id` of the item at the
`suggest_outfit` call and comparing it to `session["selected_item"]["id"]`.

**Why this target:**
5 of 5 because the agent should use the item it found when generating an
outfit, and passing a different item would make the whole response incorrect.
This is plain code with no model involved, so there's no randomness to excuse a
miss.


---

## 4. Something about the fit card

<!-- YOU WRITE THIS ONE.

     The fit card calls a model, so the same input can produce different words
     each time. That's not a bug — it's the nature of the tool. So what would
     make it acceptable?

     Think about what you'd actually be unhappy to see. A caption that never
     mentions the price? Two different items producing the same opening
     sentence? A card longer than a caption anyone would post? Any of those can
     be turned into a number. -->

Given a query that leads to a successful outfit suggestion, the agent creates a
fit card of two to four sentences that mentions the selected item, its price,
its platform, and one style word (for example "vintage" or "streetwear") — in
at least 4 of 5 tries.

**Why this target:**
4 of 5 because the fit card is generated by a model, so its wording may vary
from run to run, but it should consistently include the required information,
since the item, price, and platform were already collected earlier in the run.


---

## 5. Your choice

<!-- YOU WRITE THIS ONE TOO.

     Pick something you actually care about getting right. Speed, the empty
     wardrobe path, what happens when the model can't be reached, whether the
     search respects a price ceiling — anything, as long as it names a number
     or an observable outcome. -->

Given a query that leads to an outfit suggestion, the suggestion pairs the found
item with a piece from a different category in the wardrobe (a top with a
bottom, for example), not two pieces of the same category. A dress is exempt
because it is already a complete outfit. Target: at least 4 of 5 tries.

**Why this target:**
4 of 5 because the outfit is generated by a model, so its pairing choices will
vary, and some items (like a dress) don't need a pairing at all.
